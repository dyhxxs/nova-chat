# Nova Chat 知识库评测

## 评测目标

评测当前个人资料库的检索 baseline，回答三个工程问题：

1. 标注来源能否进入前 5 个结果；
2. 多来源问题是否同时覆盖需要的资料；
3. 没有依据和包含提示词注入的资料能否被单独识别和记录。

本评测只测 Gateway 的检索层，不把检索结果当成模型回答质量，也不把本机延迟当成生产性能。

## 数据集

数据集位于 [knowledge_eval.json](evaluation/knowledge_eval.json)，明确标记 `synthetic: true`。共 80 条问题：

- 40 条单文档可回答问题；
- 20 条跨文档可回答问题；
- 10 条应当拒答的问题；
- 10 条安全注入夹具问题。

数据集包含 10 份合成资料，使用固定文档 ID、标题和正文。问题标注了期望来源 ID；评测运行时将资料写入内存 SQLite，不会读取真实用户数据、线上数据库或 API Key。

## 运行方式

在仓库根目录执行：

```powershell
npm run knowledge:evaluate
```

对比两种检索排序策略并生成差异报告：

```powershell
npm run knowledge:compare
```

也可以指定数据集和输出目录：

```powershell
node --import tsx scripts/evaluate_knowledge.mjs `
  --dataset docs/evaluation/knowledge_eval.json `
  --output-dir artifacts/knowledge-evaluation
```

脚本直接复用 `services/gateway/src/knowledge.ts` 的 `KnowledgeStore`，因此评测的是当前实际检索逻辑。输出文件为：

- `report.json`：逐条结果、来源、延迟和失败案例；
- `report.md`：适合审查和面试展示的汇总报告。

运行 `npm run knowledge:compare` 时，输出目录为 `artifacts/knowledge-evaluation-compare`，报告会同时记录 `lexical` 默认策略和 `bm25` 实验策略，以及 BM25 相对 lexical 的指标差值。

`artifacts/` 被 Git 忽略，生成报告不会把运行结果、数据库或用户内容提交到仓库。

## 指标定义

- **Recall@5**：可回答问题中，至少一个期望来源出现在前 5 个去重来源的比例；
- **来源覆盖率**：期望来源可能有多个时，前 5 个结果覆盖期望来源的平均比例；
- **来源精确率**：可回答问题返回的前 5 个去重来源中，属于期望来源的比例；这是检索来源指标，不等于模型最终引用正确率；
- **拒答准确率**：标注为应拒答的问题是否没有返回来源；
- **注入检索命中率**：安全夹具问题能否找到预期夹具资料，不能证明模型会抵抗提示词注入；
- **平均 / P95 检索延迟**：当前 Node 进程在合成内存 SQLite 上的测量，不代表移动设备、Docker 或线上服务的延迟。

## 一次参考运行

以下结果来自 2026-10-19 的本地参考运行。它们用于记录 baseline 和失败案例，延迟随机器、Node 版本和负载变化，不是发布承诺：

| 指标 | 结果 |
| --- | ---: |
| Recall@5 | 93.33% |
| 来源覆盖率 | 88.33% |
| 来源精确率 | 73.58% |
| 拒答准确率 | 60.00% |
| 注入检索命中率 | 100.00% |
| 平均检索延迟 | 0.533 ms |
| P95 检索延迟 | 1.618 ms |

当前失败案例会保留在生成的 Markdown 报告中，包括管理员初始化口令、反向代理、`X-Request-ID` 的词法召回不足，以及含有常见词的拒答误召回。这些结果说明 baseline 仍有改进空间，不能只展示 Recall@5 而省略拒答和来源精度。

## 当前实现和策略对比

当前默认检索实现是 SQLite FTS5 加词法排序：中文使用 Han bigram，英文、数字和代码术语按词处理；资料切成约 1200 字符片段，每份资料最多返回 3 个片段，整个结果最多 6 个来源。资料片段进入模型前会被标记为不可信数据，不能改变系统规则或授权工具调用。

第二个可切换方案是 SQLite FTS5 内置 BM25 排序，通过 `KnowledgeStore.search(userId, query, 'bm25')` 使用；部署时也可以设置 `KNOWLEDGE_RETRIEVAL_STRATEGY=bm25`，网关默认仍使用 lexical。2026-10-19 在同一合成集上的对比结果如下：

| 指标 | lexical | bm25 | BM25 - lexical |
| --- | ---: | ---: | ---: |
| Recall@5 | 93.33% | 93.33% | 0.00 pp |
| 来源覆盖率 | 88.33% | 88.33% | 0.00 pp |
| 来源精确率 | 73.58% | 73.58% | 0.00 pp |
| 拒答准确率 | 60.00% | 60.00% | 0.00 pp |
| 注入检索命中率 | 100.00% | 100.00% | 0.00 pp |

这次资料规模较小且多数资料只有一个片段，BM25 没有带来离线质量变化；默认策略继续使用 lexical，因为规则更容易解释，同时保留 BM25 作为可审计的第二个排序基线，后续可以在长文档、更多重复片段和真实脱敏资料上继续比较。每次改动都应保留 JSON 报告、失败案例和运行环境，避免把合成数据结果写成真实企业指标。

模型层还需要单独增加带人工或规则标注的回答评测，才能测量引用是否支持具体陈述、拒答文本是否合适、提示词注入是否被阻断，以及上游调用成本。这些指标没有在本 baseline 报告中冒充已经完成。
