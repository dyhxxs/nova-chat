# 开发目标与路线图

## 1. 第一阶段：建立求职版项目（第 0 阶段）

### 目标

从原项目建立一个干净、可回滚、用于求职展示的版本。原项目继续保留，不在没有备份的情况下删除或大规模重写。

### 建议操作

1. 为求职版建立独立分支，例如：

```text
portfolio/nova-chat-platform
```

2. 如果使用新目录，只复制源码、配置模板、测试、正式文档和必要资源；不要复制：

- `node_modules`；
- `.env`；
- 数据库和上传目录；
- API Key、Token、密钥文件；
- 临时截图和 XML；
- 自动生成的运行报告；
- 与最终产品无关的个人工作记忆文件。

3. 统一版本号、README、变更记录和测试数量。
4. 确认以下命令在干净环境中可以执行：

```powershell
npm ci
npm run verify
npm run build
```

### 阶段验收

- 新项目可以从 README 运行；
- 原项目没有被破坏；
- 工作区没有敏感文件；
- 类型检查、测试、lint 和构建通过；
- 项目名称、版本号和截图没有互相矛盾。

## 2. 第二阶段：收敛产品范围（第 1 周）

### 核心产品问题

用户希望在手机或 Web 端使用多个模型服务，同时保留自己的资料、账户和对话，并能够以较低成本进行自托管部署。

### 本阶段保留的核心功能

- 注册、登录和 Session 管理；
- 管理员配置模型服务；
- 普通用户进行流式聊天；
- 上传资料并进行知识库问答；
- 资料按用户隔离；
- 错误、取消、断线和重试；
- Docker 启动和健康检查。

### 本阶段暂时冻结的功能

- 新增更多人物设定；
- 新增更多图片风格；
- 新增更多外部工具；
- 新增社交功能；
- 新增复杂推荐系统；
- 没有评测数据支撑的模型优化。

### 需要产出的文档

新增或整理：

```text
docs/PORTFOLIO_CASE_STUDY.md
docs/DEMO_SCRIPT.md
docs/EVALUATION.md
```

`PORTFOLIO_CASE_STUDY.md` 只回答六个问题：

1. 项目解决什么问题；
2. 为什么采用移动端加网关架构；
3. 最难的三个技术问题是什么；
4. 如何保证权限、安全和错误隔离；
5. 如何评测 AI 功能；
6. 当前有哪些限制。

## 3. 第三阶段：建立知识库评测（第 2 周）

### 数据来源

第一版不需要真实企业数据，可以使用：

- 自己编写的 10 到 20 篇产品和技术文档；
- 公开许可的技术文档；
- 当前项目的 README、架构文档、部署文档和安全文档；
- 根据文档生成、再经过人工检查的测试问题。

所有合成数据都要在文档中标记为合成数据。

### 测试集规模

第一版建议 80 到 100 条：

- 40 条资料中存在明确答案的问题；
- 20 条需要结合多个文档的问题；
- 10 条资料中没有答案、系统应该拒答的问题；
- 10 条提示词注入和越权问题；
- 可选增加 10 条中英文混合、数字和代码问题。

### 推荐数据格式

```json
{
  "id": "qa_001",
  "question": "第三方 API Key 保存在哪里？",
  "answerable": true,
  "expected_points": [
    "保存在网关侧",
    "使用主密钥加密",
    "普通用户不能读取"
  ],
  "expected_sources": [
    "SECURITY.md"
  ],
  "category": "安全设计",
  "risk": "medium"
}
```

### 评测指标

至少记录：

- `Recall@5`：正确资料是否出现在前五个结果中；
- 引用准确率：回答引用的文档是否真的支持答案；
- 关键点覆盖率：标准答案中的关键点被覆盖了多少；
- 拒答准确率：没有依据时是否拒答；
- 越权拦截率；
- 平均响应时间；
- P95 响应时间；
- 每次请求成本；
- 模型和检索方案的版本。

### 本阶段验收

- 测试集保存在版本库中；
- 评测脚本可以一条命令运行；
- 每次评测会生成 JSON 和 Markdown 报告；
- 能够比较至少两个检索方案；
- README 中只写真实跑出来的结果。

## 4. 第四阶段：完善检索能力（第 3 周）

### 当前基线

保留当前词法检索作为 baseline，不要直接删除。先记录它的效果和延迟。

### 目标方案

实现下面的检索流程：

```text
用户问题
  -> 文本清洗和查询改写
  -> FTS5/BM25 关键词检索 Top 20
  -> 向量检索 Top 20
  -> 合并去重
  -> RRF 或重排序
  -> 选择上下文
  -> 模型生成带来源回答
```

向量存储方案按部署复杂度选择：

1. 优先选择适合当前 SQLite 自托管方案的本地向量存储；
2. 如果本地依赖不稳定，先使用 FTS5 加进程内向量索引完成实验；
3. 不要为了使用向量数据库而引入一整套无法解释的基础设施。

### 必须保留的行为

- 找不到依据时明确说明；
- 返回来源文档和章节；
- 资料属于其他账户时不能检索到；
- 文档中的“忽略系统规则”等内容不能直接改变系统行为；
- 生成建议不能绕过权限和人工确认。

### 本阶段验收

初始目标可以设为：

- 可回答问题的 `Recall@5` 达到 80% 以上；
- 引用准确率达到 80% 以上；
- 无答案问题拒答准确率达到 90% 以上；
- 混合检索相较 baseline 有可解释的改进；
- 评测结果中记录失败案例，而不是只展示成功案例。

目标是评测标准，不是没有证据就可以写进简历的结果。

## 5. 第五阶段：稳定性和安全验收（第 3 到第 4 周）

### 必须验证的安全行为

- 普通用户不能读取管理员模型 Key；
- 一个用户不能读取另一个用户的资料和附件；
- Session 过期或撤销后，旧连接不能继续生成；
- 禁用用户不能登录或继续使用旧连接；
- WebSocket 断线不会导致重复计费；
- 上游错误不会把私有 URL、Key 或原始错误正文返回给用户；
- 上传文件类型和大小受到限制；
- 工具调用有白名单和参数校验；
- 生产环境不允许使用弱主密钥；
- 日志和诊断报告不包含令牌、密码、API Key 和聊天正文。

### 必须验证的稳定性行为

- 模型服务不可用时显示可理解的错误；
- 用户主动取消后，服务端任务正确清理；
- 流式生成失败后，部分回答不会污染下一轮上下文；
- 重复请求 ID 不会重复提交有费用的任务；
- 多个会话同时生成时状态不会串线；
- 数据库升级后旧数据仍可读取；
- Docker 重新启动后数据仍然存在。

### 本阶段验收

```powershell
npm run verify
npm run build
docker compose up -d --build
```

然后完成一次从注册到问答的完整演示，并保存脱敏日志。

## 6. 第六阶段：发布和求职材料（第 4 周）

### 最终交付物

- 干净的 Git 仓库；
- 一份 3 到 5 分钟演示视频；
- 一份架构图；
- 一份评测报告；
- 一份安全设计说明；
- 一键启动说明；
- 10 到 15 张必要截图；
- 一段中文简历描述；
- 一段英文项目描述；
- 10 个面试问题和答案。

### 演示视频顺序

1. 展示项目定位；
2. 登录并配置模型；
3. 上传一份资料；
4. 提出一个能找到答案的问题；
5. 展示来源引用；
6. 提出一个无答案问题，展示拒答；
7. 展示用户权限隔离；
8. 展示 Docker 或部署方式；
9. 展示测试和评测报告。

不要在视频里平均展示所有功能。让面试官记住一条完整、可靠的用户流程。

---

## 7. 暂时不要做的事情

- 不要重新写一个完全不同的聊天项目；
- 不要为了显示技术栈而加入 Kafka、Kubernetes 等不需要的组件；
- 不要在没有评测集的情况下反复更换模型；
- 不要先做模型微调；
- 不要继续堆人设和 UI 小功能；
- 不要宣称“生产级”而没有真实部署和监控证据；
- 不要删除原项目的测试来掩盖失败；
- 不要复制或提交真实 API Key、数据库和用户数据。

## 8. 推荐的开发节奏

每天有 2 小时：预计 4 周完成求职版第一版。

每天有 4 小时：预计 2 周完成求职版第一版。

每一天都要留下一个可检查的产物：

- 一份文档；
- 一组测试；
- 一条评测结果；
- 一个可以演示的功能；
- 或一个已记录的失败案例。

不要用“今天研究了一下”作为完成标准。
